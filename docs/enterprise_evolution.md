# 行为精排演进位（BehaviorRanker 演进路线图）

> 文档定位：**不用写代码的演进位**。回答常被问的局限 1——
> 「你们排序用的是规则 tagfirst，企业里排序是 CTR/GMV 行为模型，你怎么做？」
>
> 答案不是「以后再说」，而是：**精排接口已就位、行为特征清单已列、数据来了怎么接已钉死，
> 现在缺的只是行为数据本身**。本文把这条演进主线讲透。

---

## 1. 现状：冷启动精排（为什么是它）

- 当前唯一启用精排 = `ColdStartRanker`，输出 `(标签分, 热度, BM25)` 字典序（tagfirst）。
- **为什么**：本库数据是 Amazon Beauty 静态快照，**没有曝光/点击/转化/成交埋点**——
  无 CTR、无 GMV、无加购率，任何行为模型都没有训练数据。
- 冷启动策略（行业标准做法）：用**内容代理信号**代替行为信号——
  - 标签分（ts）= 用户显式约束的匹配度（唯一绝对主序，12 通道消融实证：A 通道 94.7% 最优）；
  - 热度（heat）= 评分 ×（1 + 评论量加成）→ 打包「质量 + 口碑规模」，自带反冷门；
  - BM25（文本）= 约束语义与商品标题/描述的相关度。
- 结论：**没有行为数据时，内容特征 + 规则排序是最优解；行为模型是数据就位后的升级，不是推翻。**

## 2. 演进目标：LambdaRank 双塔行为模型

企业（含 pangu 排序模块）的通用形态：

```
召回（多路并集）
  → 粗排（轻量模型，候选池 top-K）
  → 精排（LambdaRank 双塔，行为特征 CTR/GMV）
  → 业务重排（避雷 / 防资损 / 多样性）
```

beauty_agent 已落地骨架：`召回(recall_router) → 精排接口(ranker) → 避雷硬过滤(agent 内)`。
演进位要补的 = **精排这一层的模型从「规则」换成「LambdaRank 双塔」**，管线形状不变。

### 双塔结构（业界标准做法）
- **Query 塔**：用户请求特征（约束编码、肤质画像、历史交互向量、价格带偏好）。
- **Item 塔**：商品特征（标签、类目、价格、热度、差评主题、品牌）。
- **交互层**：内积 → LambdaRank 目标（pairwise 排序损失）→ 输出排序分。
- **在线 Serving**：Item 塔向量预计算（商品侧离线）、Query 塔在线推理 → 向量内积 top-N 重排。

## 3. 特征清单（BehaviorRanker 已列，代码即文档）

`scripts/ranker.py` 的 `BehaviorRanker` 类内已把行为侧特征钉死：

| 维度 | 特征 | 说明 |
|---|---|---|
| 流量 | 曝光 / 点击 / 转化 | 行为原始量 |
| 效率 | CTR / 加购率 / 成交(GMV) | 归一化效率指标 |
| 个性化 | 价格带拟合度 | 用户历史价格偏好 vs 商品价格 |
| 时间 | 近 30 天复购 / 热度 | 时效衰减 |
| 质量 | 差评规避后转化 | 差评主题过滤后重新统计的转化 |

接入行为模型**不改调用点**（`agent._retrieve → self.ranker.rank(...)`），
只改 `config.RANKER = "behavior"` 一行。工厂 `get_ranker()` 已支持。

## 4. 数据从哪来（行为数据补齐 → 训练管线）

当前缺的不是模型，是**数据**。补齐路径：

1. **埋点扩展**（复用现有 harness 埋点骨架 `harness_trace.jsonl`）：
   - 每条推荐记录加 `recommended_asins`（已有）+ 补 **曝光 = 展示位次、点击、加购、成交(GMV)** 事件流；
   - 现有 `trace_id / uid / query / constraints / recommended_asins / elapsed_ms` 已是事件流雏形，
     扩展为「请求 → 曝光 → 点击 → 转化」标准行为漏斗。
2. **训练样本组装**：
   - 正样本 = 有成交/加购的 (query, item)；
   - 负样本 = 曝光未点击 / 随机采样（业界标准负采样策略）；
   - 组成 pair，喂 LambdaRank。
3. **离线训练**（pangu 同款链路）：样本 → 特征工程 → 双塔训练 → 离线评测（NDCG/CTR-AUC）→ 上线。

## 5. 上线与评测闭环

| 阶段 | 动作 | 验收 |
|---|---|---|
| A. 埋点 | 行为事件流上线，积累 N 周 | 曝光/点击/转化全链路可归因 |
| B. 训练 | LambdaRank 双塔离线训练 | 离线 NDCG / CTR-AUC 显著优于 tagfirst |
| C. 上线 | `config.RANKER="behavior"`，影子/小流量对照 | 在线 CTR@k、GMV@k 提升；锚点零回归 |
| D. 闭环 | 持续回灌行为数据重训 + 消融 | 每轮上线前跑 12 通道消融确认主序稳定 |

**评测指标升级**（现有 `eval_compare.py` 扩展，不只内容 NDCG）：
- 行为侧：`CTR@k`（k 位曝光点击率）、`GMV@k`、`加购率@k`；
- 内容侧：现有首答命中率 / NDCG@5 / 避雷 0.889 / 资损 8/8 保持不变，作为**回归红线**。

## 6. 为什么这样设计（项目叙事）

- **接口在前，数据在后**：冷启动精排把「换模型」的接缝留好（`config.RANKER` 一行切换），
  数据来了只加模型、不动管线——这是可演进架构的关键。
- **诚实边界**：`BehaviorRanker` 未训练；被选中时安全降级冷启动 + 显式警告，绝不崩 Demo。
  对外按「接口就位 → 特征已列 → 数据是局限 → 演进路径明确」四步讲，不虚报能力。
- **对齐 pangu**：与实习项目「粗排 → 精排（CTR/GMV/LambdaRank）→ 业务重排」的模块形状一致，
  是「把企业级工程能力搬到小项目」的最直观证明。

## 7. 与 MVP 的关系

- MVP 交付的是**检索链路骨架**：多路召回 + 路由 + 精排接口 + 配置中心（`recall_router.py / ranker.py / config.py`）。
- 本文是这条主线的**演进位**：不新增代码，只把「未来怎么走」钉在文档，让项目看起来像
  **有完整演进规划的工程系统**，而不是一次性的规则脚本。
