# Phase 2 导购 Agent 设计文档（3 决策节点 + 3 指标 + CONTRACT）

> 一句话定位：导购 Agent 不是写死的线性脚本，而是一套**可自执行的标准流程**——
> 「要不要追问 / 检索不到要不要改写重试 / 无解要不要兜底」是三个**显式决策节点**，
> Agent 根据约束抽取结果自判断、自执行、自修复，每条决策都落成结构化记录，可断言可复盘。
>
> 核心交付（全部零模型 key 可复现）：
> `agent.py`（Agent 本体）+ `contract_cases.py`（24 题 CONTRACT 断言）+
> `eval_agent.py`（跑批：硬断言通过率 + 3 决策指标 + 软指标）。

---

## 0. 为什么这样设计

检索层（Phase 1）解决了「给商品排序」，但排序不等同于「能帮用户选」。真实导购要回答三个排序答不了的问题：

| 排序层答不了 | 导购 Agent 决策节点 |
|---|---|
| 用户啥都没说清楚，推什么都像瞎猜 | **节点①追问**：该问的问，不该问的绝不打扰 |
| 说了「防水」，但去坎昆的场景还隐含「防晒」 | **节点②改写重试**：场景归因扩展召回 |
| 又要强控油又要强保湿，库里没这种东西 | **节点③诚实兜底**：直说无解 + 替代方向，不硬推 |

设计原则：**每个节点都有明确的触发条件（可复现规则）+ 明确的失败处理（诚实优先）**，
不是脚本 if-else 堆出来的一次性话术，而是可以迁移到任何品类、任何 query 的流程骨架。

## 1. 编排总览

```
用户 query（原始文本）
  → ① 约束抽取 extract_constraints（纯文本关键词规则，8 键 req + 12 项 meta）
  → ② 决策节点「追问」decide_ask
       ├─ ask_all / ask_first / ask_shade_soft → 输出问题清单，本轮回合不推荐
       └─ no_ask → 继续
  → ③ 检索 _retrieve（复用 ProductIndex：全库混合打分 + 后置硬过滤）
  → ④ 决策节点「改写重试」decide_retry
       └─ 硬过滤后可用候选 <2 → rewrite_query 注入隐式词 → 重试一次
  → ⑤ 生成 _build_evidence / _build_reply（grounding：只引用命中商品事实 + 四件套）
  → ⑥ 决策节点「诚实兜底」decide_fallback
       ├─ 矛盾无解（又油又干同时存在）→ 直说 + 替代方向（level=full）
       └─ 换季「一件到底」→ 诚实附注 + 仍推平衡型（level=honest_note）
  → 输出：结构化决策记录 dict（对话 demo 和 CONTRACT 断言消费同一份）
```

每次 `agent.run(query)` 返回一条完整决策记录：

```json
{
  "query": "...",
  "constraints": {"hard": [], "soft": [], "finish": null, "coverage": null,
                  "form": null, "shade_dir": null, "budget": null, "implicit": [],
                  "unsolvable": false, "seasonal": false, "newbie": false,
                  "control_oil": false, "negative_axes": []},
  "ask": {"decision": "ask_all", "questions": ["..."]},
  "retry": {"triggered": false, "rewrite": ""},
  "fallback": {"triggered": false, "level": "", "message": "", "alternatives": []},
  "recommendations": [{"asin": "...", "title": "...",
                       "evidence": {"tags": "...", "price": "...", "budget_status": "...",
                                    "rating": "...", "heat": "...", "link": "🔗asin",
                                    "citation": "依据：...", "honest": []}}],
  "avoided": [{"asin": "...", "title": "...", "reason": "..."}],
  "reply": "面向用户的回复文本"
}
```

## 2. 决策节点①「追问」

**触发规则**（用户已验收定稿）：

| 决策 | 触发条件 | 追问数 |
|---|---|---|
| `ask_all`（强制追问） | 缺失关键约束（肤质/妆效/遮瑕/色号）≥3 **且**无强意图（强意图=有任一硬/软/妆效/遮瑕/质地/色号/熟龄/控油/持妆信号） | 一轮合并问完独立约束，问题数=缺失约束数 |
| `ask_first`（首问一个最改变方向的约束） | 核心意图清楚但缺一个会翻转候选的约束（例：控油≠哑光，D-2 先问妆效） | 1 个 |
| `ask_shade_soft`（色号软追问） | 预算类 + 约束较全仅缺色号 | 1 个，**附在推荐末尾**，不强制 |
| `no_ask` | 约束齐（直说/色号/质地/持妆/硬约束类） | 0 |

**关键设计点**：

- **追问数 = 缺失的关键约束数**：缺 3 个就一次性问 3 个，不挤牙膏式反复打扰。
- **合并式 + 友好预期**：所有问题一轮问完，回复以「为了更好帮您筛选商品，请先回答几个问题」开场。
- **预算属软约束**：预算缺不终止追问（问完肤质/妆效后照常问预算），但预算只是排序权重，不参与缺失计数。
- **色号是软追问**：约束基本齐全、只缺色号时不打断，推荐末尾附「告诉我常用色号（偏自然/偏白）可更精准」。
- **新手引导**：`newbie` 信号（never used / new to / where should I start）触发引导式问法（判断肤质→裸妆还是遮瑕强）。
- **矛盾需求不追问**：检测到又油又干同时存在 → 直接跳兜底节点，不浪费用户时间。

**实测分布（24 题）**：追问率 = 7/24 = 29.2%
（ask_all=4：模糊/新手/预算极紧；ask_first=1：控油≠哑光；ask_shade_soft=2：预算+缺色号）

## 3. 决策节点②「改写重试」

**触发条件**：检索硬过滤后可用候选 < 2（敏感肌/痘痘肌/质地/遮瑕/预算/缺陷证据把候选过滤没了）。

**做法**：复用意图推理层 `infer_implicit(intent, query)` 收集隐式改写词，`rewrite_query` 在句末注入
（如「去坎昆+防水」→ 注入 `waterproof SPF`），重试**一次**，不无限循环。

**为什么需要它**：用户常只说「症状」，不说「需求」。
- 说「防水」→ 户外/水上场景隐含防晒（坎昆 → `防晒` + `防水持妆`）。
- 说「消除油光」→ 隐含油皮/混油 + 哑光妆效。
- 说「保湿」→ 隐含干皮/混干。

硬过滤后无解，说明当前改写维度检索不到，注入隐式关键词扩展召回后再排一次。重试后仍无解 → 交给兜底节点，**不会硬凑**。

**实测分布（24 题）**：降级率 = 0/24 = 0.0%（24 题硬过滤后都有 ≥2 个可用候选，重试未触发）。
这个 0 是有意义的：说明硬过滤设计得合理，没有把「完全能答」的题误判成无解。

---

## 4. 决策节点③「诚实兜底」

**原则**：检索层答不了的时候，**诚实的「没有」比硬推的「沾边」更专业**。两条兜底路径：

| 场景 | level | 行为 |
|---|---|---|
| 矛盾需求无解（又油又干**同时**存在：T 区油+脸颊起皮） | `full` | 直说「库里没有能同时强控油+强保湿的单品」+ 给 5 条平衡型/分区处理替代方向，**不推进推荐列表** |
| 换季「一件到底」（冬干夏油想一瓶全年） | `honest_note` | 诚实附注「没有粉底会自动调肤」，仍推平衡型 + 极端季节微调护肤/分区用 |

**矛盾检测规则**：`oily/dry 同时出现` + `at the same time / simultaneously / T-zone` + `both`，且非换季（winter+summer 分离不算矛盾）→ `unsolvable=True`。

**实测分布（24 题）**：兜底率 = 2/24 = 8.3%（id20=honest_note，id21=full）。

## 5. grounding 与诚实性规范（生成层）

推荐条目的证据**只用库里命中商品的事实** + `tag_score` 返回的命中原因，四件套固定：

- **标签**：form_tag + skin_tags + finish_tag + coverage_tag（只在 query 指定色号方向时附 shade_tag）
- **价格**：库内快照。**缺价标「价格待核实」绝不虚构**；真实场景接实时价格 API。
- **口碑**：评分 + 评论数（例 `4.7分/94条`）
- **热度分档**：高≥200 / 中 50-199 / 低<50
- **链接**：🔗asin 占位

三条硬规矩（来自用户复核意见）：

1. **只 cite query 实际指定的轴**。query 没提色号 → 推荐里绝不出现「色号白皙」判断（id3 用户批「没答色号直接判断白皙？」）。
2. **未标轴诚实标注，不硬吹**。商品遮瑕度/肤质库内未标 → 固定附「该商品遮瑕度库内未标，需确认」。
3. **预算型诚实处理缺价**。77% 商品无价，不瞎报价、不排除缺价商品，按档位标「价格待核实」。

推荐结构：预算查询固定「2 预算内 + 1 微超升级位」；其余取 top-3。

## 6. 3 决策指标（eval_agent.py 统计）

| 指标 | 定义 | 24 题实测 | 期望 |
|---|---|---|---|
| **追问率** | 触发追问（ask_all/ask_first/ask_shade_soft）的 query 数 / 24 | **7/24 = 29.2%** | 模糊/预算缺信息类高，直说/色号/质地/硬约束类低 |
| **降级率** | 触发改写重试的 query 数 / 24 | **0/24 = 0.0%** | 硬过滤不把「能答」误判成「无解」 |
| **兜底率** | 走到诚实兜底的 query 数 / 24 | **2/24 = 8.3%** | 无解/换季场景诚实兜底 |

三项指标分别刻画 Agent 的**主动性**（该问就问）、**自愈性**（检索不到就改写重试）、
**诚实性**（无解就直说）——三个维度加起来，才是「会自己做决定」而不是「照稿念」。

## 7. CONTRACT 断言设计（contract_cases.py）

从 24 题 notes + 用户复核意见提炼，每个 case 挂一组**硬断言**（测决策正确性，不依赖排序质量）：

| 断言族 | 覆盖题号 | 测什么 |
|---|---|---|
| 追问决策正确 | id2/4/5/6/15→ask_*，id1/3/10-12/16-19/22-24→no_ask | 该问的问、不该问的不问 |
| 兜底决策正确 | id20→honest_note，id21→full+直说+替代方向 | 无解/换季诚实兜底 |
| 硬约束过滤 | id7/9/19 肤质、id17/22 遮瑕、id23/24 质地 | 只推约束匹配的候选 |
| 假命中排除 | id23/24 KLAIRS（标题 cushion 实际乳霜） | 质地看 form_tag 值，不信标题 |
| 诚实标注 | id13/14/22 缺价/未标 | 缺价不虚报、未标不硬吹 |
| 证据齐全 | 全部 | 每条推荐含四件套 + 🔗asin |
| 不默认色号 | id3 | query 没提色号不得 cite 色号 |
| 意图完整性 | id16 坎昆 | 显式防水 + 场景规则补出防晒 |
| 缺陷证据避雷 | id7/8 | 负约束命中的缺陷商品不进推荐 |

**跑批结果**：硬断言通过率 **105/105 = 100%**（id17 query 补全后 +4 条：form=粉状 / recs_form_ok / shade=None / no_shade_citation）。

**软指标（measured，定标口径 2026-08-28；q20 泄漏修复后 2026-08-29 更新）**：
- **首答命中率 = 干净命中 top-3 = 15/19 = 78.9%（达标 70%）**
  - **口径**：candidate_pool_v2 池内（与 Phase-1 同方法学），分母 = 有推荐的 19 题（排除 ask_all/ask_first 追问题）；
    命中 = top-3 推荐里 ≥1 个正确答案（primary 或 extra）**且** 0 个避雷泄漏（negative 不进 top-3）
  - 排序 = `score_candidates("tagfirst")`（标签主序 → 热度 → BM25，2026-08-28 定标）
  - **对照口径**：严格 primary-in-top-3 = 63.2%（购物 query 多解，命中 primary 是抽签）；宽松 any-correct = 78.9%（与干净命中重合，泄漏已清零）
- **避雷率**：v2 池内负例泄漏 **0/19**（q20 泄漏已修复，见 §8.7）；CONTRACT 全库跑批避雷仍 100%（决策层缺陷证据兜住）

> 口径说明：首答命中率是 Phase-2 的**核心目标指标**（用户定标），与决策正确/诚实性并列为三支柱。

## 8.5 二期：模糊意图兜底 → LLM（A/B 实验，2026-08-28）

**实验问题**（核心）：规则表覆盖不了用户的隐藏意图（"去海边度蜜月"隐含防晒+防水），**什么时候该上 LLM？** 用 A/B 对照回答：A = `GuideAgent()` 纯规则（锚点 73.7% 回归护栏），B = `GuideAgent(intent_mode="hybrid")` 规则+LLM 兜底。

**设计四要素**（详见 `database_schema.md §7.9`）：
1. **触发 = 规则完全盲区**：`should_fallback` 要求规则**无任何可检索信号** + query 含语境线索词才调 LLM。
2. **LLM 输出强制结构化 JSON**：`{"意图":[…], "约束":{…}, "证据":"…"}`，DeepSeek `deepseek-v4-flash`，temperature=0。
3. **信任信号 = 检索兑现率（不用 LLM 自报置信度）**：意图→规范轴→库内兑现数 ≥20→检索 top-8 兑现占比 ≥0.5→才采信。
4. **降级链**：LLM 超时/断连/解析失败/兑现不了 → 静默降级回规则。

**两个修复（实验逼出来的边界认知）**：
- **锚点漂移**：v1 触发条件只查 `implicit` 空 + 线索词 → 锚点题 q8 被 "settle" 误拉进 LLM，LLM 把 "lasts all day" 过度推断成防水持妆、污染排序 → 锚点 14→13。加 `_rule_has_signal` 闸门（规则已有任一信号绝不上模型）修复，锚点回 73.7%。
- **妆效丢失**：LLM 常把妆效写在「约束.妆效」不在"意图"列表（q27/33）→ v1 只读"意图"→ 哑光丢失 + 控油无妆效被 D-2 追问截胡 → CASES_HIDDEN 6/9。并入 `validate` + 采信哑光时同步 `finish="哑光"` → 9/9。

**结果（实测定稿）**：锚点 A/B 均 14/19=73.7%（零漂移）；hidden 盲区题 A 0/9 → B **7/9 可答、7/9 命中**；31/32（熟龄肌/轻薄质地）= 模型识别出但库兑现不了 → 诚实降级 A==B；CONTRACT CASES 105/105、CASES_HIDDEN 9/9。

**结论**：LLM 的价值 = 规则的漏。规则能覆盖的 19 题，LLM 掺和反而掉分；规则盲区的 9 题，LLM 救回 7 题、2 题诚实降级。

## 8.6 规则参数校准：人工抽检 + 70% 负面共识 → 硬规则（2026-08-28）

**问题**：避雷「硬规则」怎么定才是对的？监督/RL 在 demo 阶段做不了（无环境/无奖励流），选**规则参数校准**路线：把「评论负面反馈」当成监督信号，校准规则的判定参数。

**闭环三件事**（`agent._load_defect` 的核心机制升级）：
1. **人工抽检 gold**：10 条关键题 → 4 PASS + 6 MODIFY（`human_gold_check` 表），MODIFY 全部指向「标签≠真实口碑，要看评论区」。
2. **gold 真值校准**：6 条 MODIFY 落库（`calibrate_gold.py`，条目级复用保留语义批注，三处同步 + 备份 *_bak_v17）。
3. **70% 负面共识 → 硬规则**（`defect_consensus.py`）：某缺陷轴提及数 ÷ 该商品负面评论数 ≥ **70%** → 标硬规则（命中即避雷）；负面评论数 0 → 不标；**色号偏深黄/浅灰 = 色号适配，不算避雷轴**。

**参数校准的效果**（数据说话）：
- 避雷集 122 → **78 商品**（44 个假避雷放行：新 primary Dermacol 闷痘 31%、extra Revlon 卡粉 8%、MaryKay 0 负面…）；保留真硬规则（Myconos 卡粉 86%、Rimmel 卡粉 75%）。
- **锚点零回归**：校准 + 共识升级后首答 **73.7%** 不变、CONTRACT 105/105、q8 仍 ✓ primRank=1——评论共识与引擎排序一致（Mirenesse 本就第一，Rimmel 被引擎正确排后）。

**项目叙事**：「规则不是拍脑袋定的。用户评了分 → 我拿评分当监督信号 → 6 条 gold 被校准 → 避雷硬规则按 70% 评论共识收紧。校准前后锚点 73.7% 零回归，恰好证明共识口径和引擎真实行为一致，不是改数字骗评测。」

## 8.7 全年通用混合肌 balance 规则：修 q20 避雷泄漏（2026-08-29）

**badcase**：q20「混干皮冬干夏油，想一瓶全年不换」的 v2 池 top-3 曾混入两个负例——

**修法（combo + seasonal 双闸门，balance 规则）**：
1. `req["seasonal"]` 贯通三处 req 构造（agent.extract_constraints / engine.parse_query /

   同时覆盖干皮+油皮（或全肤质）→ **+2「干油双标(全年)」**；只覆盖单边（单季品）→ **-2「单季品·降权」**。

## 8.13 对话记忆层 + 色号诊断续答系统化（2026-08-31 用户定）

**用户实测暴露的坏例**：诊断自测后用户答观察（「血管中性…橘色系显白」），Agent **没给色号结论**，

返回东西给用户之前有没有联系上下文？」——这是**上下文断开的系统性根因**，不是单个关键词漏配。

**根因（两层）**：
1. **前端没拼 AI 上一条回答**：诊断流程中用户答的是「AI 的提问」（判断色号的土办法），
   但前端 context 只拼「原始需求 + User says: 回答」，AI 问过什么完全看不到 → 闸门无法判断
   「这是回答诊断提问」，落回推荐器。
2. **缺 shade_diagnosis 意图 + 会话状态**：色号自测→结论→点头→挑款是一条**状态链**，
   原逻辑把每一步都当独立 query，无「诊断会话」概念，也无色号家族跨轮记忆。

**修法（用户确认：系统化，不逐个加关键词）**：
1. **对话记忆层（数据层）**：前端每轮把「最近 8 轮用户+AI 双方消息」`convo` 传给后端；
   后端 `_store_convo` 每轮压缩落盘到 `user_profiles.json` 的 `convo` 字段——
   `{orig 原始需求, req 抽取约束, recent 最近 6 轮双方对话, diag_family 诊断色号, updated}`。
   闸门/推荐器都从记忆取数，不再靠前端拼超长字符串。**每用户专有 user_id + 每轮存储 = 换浏览器重开也在。**
2. **shade_diagnosis 意图（工具拦截落地）**：`llm_gate.route` 新增两个规则分支——
   - 上次 AI 消息含诊断自测关键词（血管/金饰/银饰/手腕/口红/观察/自测/素颜）→ 本轮=**诊断续答**；
   - 上次 AI 消息含软询问（要不要/帮你挑/挑几款/pick a few）**且**记忆有诊断色号 → 本轮
     若用户点头（好/行/可以/要…）= **confirm_recommend**，带「原需求，色号自然」走推荐器；

## 8.14 对比/介绍人性化 + 结合评论区（2026-08-31 用户定）

**用户实测反馈**：问「这三款有什么区别吗？」，Agent 回了一整块结构化清单
（【商品名】/标签：/口碑：/色号：/差评声音：）——「回答太过于机器化，我需要人性化，
更加友好的介绍，并且必须结合评论区介绍。请固定记忆。」

**根因（两层，都是真凶）**：
1. **LLM 调用失败 → 直接甩结构化 facts**：compare 走 `llm_gate`，先拼 `_product_facts_block`
   （真实数据块），再让 LLM 改写成大白话；LLM 一挂 `text = facts` 就把数据清单原样甩给用户。
2. **更深一层：推理模型 token 预算被思考吃光**：`deepseek-v4-flash` 是推理模型，
   `max_tokens` = 推理（reasoning_content）+ 正文一起算。GEN_TOKENS=900 常被思考耗尽 →
   `content` 空/截断（HTTP 200 + `finish_reason:length` + content=""），LLM 压根没吐正文 →
   每轮都落回机器化兜底。**这正是用户踩到的直接原因**。

**修法（用户确认：口语分点式 + 结合评论区 + 兜底也讲人话）**：
1. **确定性朋友式兜底 `_compare_fallback`**（2026-08-31 用户定）：LLM 挂 → 不甩 facts，
   像朋友一样拆开讲——开头点共性与差异（如都是水光妆效但质地不同）、每款一段（🌟 开头：
   质地/适合谁 + 评论区声音[评分/条数/样本最多最稳] + 差评主题 + 价格）、结尾诚实总结 +
   反问收窄（「你更看重质地、口碑还是价格？」）。全程只用真实数据，**绝不编评论原话**。
2. **LLM prompt 改口语分点式**：`_generate_compare` 明确「不要用表格」「像朋友聊天，不要像
   数据报表」「🌟 每款一段」「把评论区声音（评分/条数/反复吐槽的毛病）讲出来」。
3. **根因修复：GEN_TOKENS 900 → 1800**（推理+正文预算，正文稳定吐出）。
4. **诚实边界（用户认可口径）**：项目里没有评论原文，能「结合评论区」的是真实从 3881 条
   评论抽出的信号——评分、评价条数、差评主题（卡粉/闷痘…）。讲人话引用这些信号，
   但**绝不编评论原话**（铁律）。

**实测**：离线桩 LLM 失败 → 兜底输出口语分点式（无【】/标签：/差评声音：标记，含 🌟 与
评论区）；LLM 路径 3/3 稳定出人性化对比（623/684/617 字，会结合用户肤质给提醒如「混油用
可能不够控油」）；HTTP 全链路推荐→问区别 通过（LLM 10-16s 推理出人话 / LLM 挂 立即出兜底人话）。
锚点零回归：首答 94.7% / NDCG@5 0.553 / 避雷 0.889 / CONTRACT 105/105 / 全库避雷 24/24
（闸门仅在多轮追问触发，eval 全英文首答不经过 → 字节零漂移）。
